TEMA 3 Seguridad en bases de datos relacionales

Comprender cómo llega una petición al dato, qué controla cada defensa y cómo recuperamos el servicio.

3.1 · La idea que organiza el tema

La base está cifrada. La consulta sigue devolviendo datos.

Una base relacional organiza información en tablas conectadas por claves. El motor recibe consultas SQL, comprueba permisos y devuelve filas. Para usar los datos tiene que poder leerlos. Por eso el cifrado de sus archivos y el permiso para consultar resuelven problemas diferentes.

En CosechaDirecta, una tienda ficticia, la web consulta pedidos y clientes. El caso tiene 48 210 clientes. Una búsqueda manipulada devuelve demasiados datos: veremos por qué ocurre y qué cambia al corregir cada capa.

Cliente U17Solicita su pedido
AplicaciónReconoce la sesión y decide el recurso
Motor SQLEjecuta con la cuenta app_web
ArchivosAlmacenamiento cifrado

La protección depende de toda la ruta: quién pide, qué recurso puede usar, cómo se construye SQL y qué permite la cuenta del motor.

Esquema del caso. El tema usa PostgreSQL para permisos y recuperación, SQLite para la demostración de consultas y SQL Server para explicar TDE. No se atribuyen las mismas prestaciones a todos los motores.

Tres objetivos, controles que se complementan

Confidencialidad

Que cada identidad acceda solo a lo que necesita.

Ejemplo: el cliente ve su pedido y el analista recibe ventas agregadas.

Integridad

Que las modificaciones estén autorizadas y podamos detectar cambios indebidos.

Ejemplo: la cuenta de la web no cambia la estructura de las tablas.

Disponibilidad

Que el servicio pueda operar y recuperarse dentro del tiempo que necesita el negocio.

Ejemplo: restaurar datos y comprobar que se pueden consultar pedidos.

La defensa en profundidad combina controles con funciones distintas. Si una petición supera una barrera, otra puede limitar el daño. Acumular herramientas sin conocer su función no demuestra que esas barreras existan.

3.2 · Quién decide el acceso

Autenticación, autorización y cuenta de servicio

Autenticar es acreditar una identidad. Autorizar es decidir si esa identidad puede realizar una operación sobre un recurso concreto. Una sesión válida no concede acceso a todos los pedidos.

U17Identidad de la persona en la web
APIAutoriza el pedido solicitado
app_webIdentidad técnica ante la base
Pedido C01Recurso de U17

El motor puede ver una única cuenta técnica para muchas personas. La aplicación necesita conservar la identidad de la sesión y comprobar la propiedad del pedido. El permiso de tabla no hace automáticamente esa separación.

La sesión es U17. Cambia el pedido que solicita.

SELECT id FROM pedidos
WHERE id = ? AND cliente = ?

La identidad U17 procede de la sesión validada por el servidor. Si el cliente pudiera elegir libremente ese segundo valor, la condición perdería su finalidad. Este modelo usa dos pedidos ficticios; el navegador no ejecuta la consulta.

DAC, MAC y RBAC organizan la decisión

DAC · propietario

Quien posee un objeto concede o retira permisos sobre él, según las reglas del motor.

El propietario de una tabla concede SELECT a otra cuenta.

MAC · política central

Una política de clasificación y autorizaciones decide el acceso. Un usuario no puede cambiarla por ser dueño del dato.

Una etiqueta confidencial se compara con la autorización del sujeto.

RBAC · función

Se agrupan permisos en roles y se asignan a las identidades que realizan esas tareas.

El rol de análisis permite leer una vista agregada.

Son modelos de decisión; un sistema puede combinar mecanismos. En este caso, el mínimo privilegio significa dar a cada cuenta las operaciones y el alcance necesarios para su tarea.

Tres funciones necesitan permisos diferentes

Si alguien puede consultar todos los correos, puede conservar el resultado. El control útil para el analista es limitar el dato accesible: una vista agregada y los permisos efectivos adecuados.

DML opera sobre datos, como SELECT, INSERT o UPDATE. DDL modifica la estructura, como CREATE o ALTER. La concesión efectiva también depende de otros roles, permisos directos y propiedad de objetos.

3.3 · Estructura y datos

La inyección aparece cuando un valor se convierte en SQL

La aplicación quiere buscar un código de producto. Si pega directamente el texto recibido dentro de la sentencia, una entrada puede cerrar el valor y añadir una condición. El motor interpreta la sentencia completa: no sabe qué parte escribió el programador y cuál llegó del cliente.

Tres productos: P01, P02 y P03

Parametrizar: el programa fija la estructura de la consulta y entrega el valor por separado. El texto que contiene una comilla o palabras SQL sigue ocupando el lugar de un dato.
consulta = "SELECT codigo FROM productos WHERE codigo = ?"
filas = conexion.execute(consulta, (entrada,)).fetchall()

En esta API de SQLite, ? representa un valor. Para elegir una columna o una dirección de ordenación, la aplicación debe seleccionar entre opciones fijas admitidas; no concatenar un identificador arbitrario.

La defensa se entiende comparando dos resultados: P01 sigue encontrándose; la entrada manipulada ya no devuelve los tres productos.

La consulta segura necesita autorización y permisos

Una consulta parametrizada todavía puede pedir un pedido ajeno. Por eso mantenemos la condición de propietario y el alcance mínimo de la cuenta técnica. Un ORM o un procedimiento almacenado también necesita construir SQL de forma segura. Un WAF puede filtrar peticiones que pasan por él; no sustituye estas decisiones dentro de la aplicación.

Comprobación breve de comprensión

La consulta usa parámetros, pero devuelve C02 a la sesión U17. ¿Qué falta?

Explicación: los parámetros impiden alterar la estructura. Falta comprobar que U17 está autorizado a leer C02. La identidad de sesión, el recurso y la acción deben formar parte de esa decisión.

3.4 · Dónde protege cada mecanismo

Reposo, tránsito y resultado de una consulta

El cifrado transforma datos para que puedan recuperarse con las claves adecuadas. La pregunta docente es dónde ocurre esa transformación y contra qué acceso protege. No basta con decir «la base está cifrada».

Archivos y logsCifrado en reposo
Motor SQL ServerDescifra al leer
Canal TLSProtege el transporte
AplicaciónRecibe datos legibles

TDE es cifrado transparente de archivos de datos y logs en SQL Server. El motor puede atender consultas sin que la aplicación descifre cada campo. TLS protege el canal y requiere validar la identidad del destino. Una consulta autorizada sigue recibiendo valores legibles.

El esquema explica fronteras; no ejecuta cifrado. Para recuperar una base TDE en otra instancia puede ser necesario su certificado y clave privada. El material de recuperación debe conservarse y probarse con los permisos adecuados.

Enmascarar cambia qué se muestra o qué copia se utiliza

Máscara dinámica

El dato original permanece. El resultado se presenta de forma reducida a ciertos perfiles.

Original: ana@ejemplo.invalid
Vista enmascarada: a***@ejemplo.invalid

Ejemplo didáctico de presentación, no una regla exacta del motor. Las máscaras tienen límites frente a consultas e inferencias y deben acompañarse de permisos.

Máscara estática y datos sintéticos

La máscara estática transforma una copia para otro uso. Los datos sintéticos se generan para las pruebas. En ambos casos hay que comprobar qué relaciones y escenarios conserva el conjunto.

Transformar nombres no garantiza que toda la copia haya dejado de identificar personas. También pueden existir identificadores indirectos y relaciones con otros datos.

El mecanismo se elige por la amenaza: archivos robados, tráfico interceptado, exposición por perfil o datos de pruebas. Ninguno corrige por sí solo una consulta que devuelve filas indebidas.

3.5 · Entender lo que pasó

Auditar una operación y recuperar datos son tareas distintas

La auditoría permite reconstruir quién hizo qué, sobre qué recurso, cuándo y con qué resultado. Un registro de transacciones ayuda al motor a recuperar cambios. Sus propósitos y contenidos no son intercambiables.

Dato del eventoEjemplo ficticioQué permite explicar
Hora y correlación09:14 · req-021Relacionar la petición web con su operación.
Identidad y recursoU17 · app_web · pedido C02Distinguir persona, cuenta técnica y dato solicitado.
Acción y resultadoLectura · denegadaObservar que la autorización rechazó el pedido ajeno.

Los registros necesitan acceso restringido, integridad, retención y revisión. Evitamos guardar contraseñas, tokens o cuerpos completos innecesarios. Una alerta avisa; la respuesta definida decide quién contiene el incidente y cómo comprueba la recuperación.

Cómo volver a un estado anterior al borrado

Una réplica puede mantener servicio cuando falla un nodo y también reproducir un borrado aceptado. Para recuperar un estado histórico necesitamos una copia utilizable y los cambios conservados que requiera el mecanismo elegido.

Ejemplo de recuperación puntual en PostgreSQL

00:00Copia física base
09:55Punto de recuperación del supuesto
10:00Borrado e interrupción
11:30Servicio restaurado y validado

Restauramos la copia base y reproducimos una secuencia continua de WAL hasta el punto elegido. Nos detenemos antes del daño. Después validamos datos, permisos y funcionamiento.

PITR requiere preparación previa y archivos WAL disponibles. Un volcado lógico pg_dump no es la copia física base de este procedimiento.

RPO y RTO miden intervalos diferentes

RPO fija cuánto retroceso de datos tolera el negocio. RTO fija cuánto tiempo de interrupción tolera hasta recuperar el servicio. El objetivo se acuerda antes; la prueba permite compararlo con una medida.

Objetivos del caso: retroceso máximo de 15 minutos y recuperación del servicio en 60 minutos.

Reducir el tiempo puede exigir mejorar la detección, preparar infraestructura, acceder a claves, restaurar con más rapidez o automatizar la validación. El ensayo debe medir desde el inicio de la interrupción hasta el servicio validado y explicitar qué operaciones posteriores al punto recuperado necesitan reconciliación.

Los botones comparan supuestos explicados, no ejecutan restauraciones ni miden el RTO de una instalación real.

La explicación completa del caso

Así se resuelve la fuga y se prepara la recuperación

El motor podía descifrar los archivos porque estaba funcionando normalmente. La fuga nacía en el alcance de la consulta y de las identidades que la ejecutaban. La corrección mantiene la operación legítima y cierra la indebida.

Comprobar la comprensión después de la explicación

Una aplicación parametriza las consultas y usa TDE, pero consulta todos los clientes con una cuenta administradora. ¿Qué dos decisiones siguen pendientes?

Respuesta razonada: autorizar el recurso y reducir el alcance de la cuenta. Los parámetros protegen la estructura SQL y TDE protege archivos en reposo; ninguno determina por sí solo qué clientes necesita leer esa petición.

Para contrastarlo por parejas: una persona propone el permiso y otra identifica una operación legítima que debe seguir funcionando. Se acuerdan una prueba positiva y otra negativa.
