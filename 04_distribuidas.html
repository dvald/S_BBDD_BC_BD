TEMA 4Cómo proteger bases de datos NoSQL

Del documento que guarda un catálogo a las identidades, consultas y conexiones que lo protegen.

4.1–4.2 · El modelo de datos

Una tienda necesita guardar datos con formas diferentes

Un producto puede tener fotografías, variantes y atributos que otro producto no tiene. Una sesión necesita una búsqueda rápida por su identificador. Una lectura de un sensor se consulta por dispositivo y tiempo.

NoSQL agrupa sistemas que utilizan modelos distintos del relacional tradicional. El modelo determina cómo organizamos y consultamos la información. La seguridad sigue exigiendo decidir quién puede acceder, a qué datos y con qué operaciones.

MongoDB: un producto en un documento

El documento reúne los campos del producto. Puede contener listas y objetos anidados. La aplicación consulta por campos del documento y el motor interpreta la estructura del filtro.

Consecuencia para la seguridad: si se acepta un objeto del cliente como condición, puede introducir operadores que cambien la selección.

Catálogo de CosechaDirecta

{
  "codigo": "P01",
  "nombre": "Tomates",
  "variantes": ["caja", "granel"],
  "publicado": true
}

Operación del caso: buscar un producto por su código.

Cambiar el modelo de almacenamiento cambia las consultas y los permisos que debemos revisar. «NoSQL» no significa que las entradas dejen de poder alterar una consulta.

El dato puede alcanzarse por más de un camino

En CosechaDirecta, el visitante consulta la API. La API utiliza una cuenta técnica para leer el catálogo. Los miembros del clúster intercambian cambios. Un cliente que alcance directamente el motor evita por completo la validación de la API.

La identidad del visitante y la cuenta técnica cumplen funciones distintas. La API limita la petición; el motor limita las operaciones que puede ejecutar su cliente.

Problema que resolveremos: la API ya rechaza un objeto mal formado, pero una ruta directa todavía permite leer borradores. Necesitamos entender y proteger ambas rutas.

4.3 · Inyección NoSQL

Un valor de búsqueda se convierte en una instrucción

La API espera un código como "P01". Si admite cualquier JSON y lo coloca dentro del filtro, el cliente también puede enviar {"$ne":"P01"}. MongoDB interpreta $ne como «distinto de».

El error aparece al permitir que una entrada controle la estructura de la consulta. No hace falta introducir una sentencia SQL ni romper comillas. Observa cómo cambia el significado al recorrer los cuatro pasos.

  1. Entrada
  2. Filtro
  3. Selección
  4. Respuesta

1. La API recibe un dato

El cliente envía un código. Esta ruta sin contrato acepta cualquier estructura JSON como valor de codigo.

{"codigo": "P01"}
P01 · TomatesPublicadoDocumento del catálogo
P02 · ManzanasPublicadoDocumento del catálogo
P03 · Cesta futuraBorradorDocumento del catálogo

Modelo didáctico calculado en el navegador sobre estos tres documentos, todos con el campo codigo. No consulta un servidor MongoDB. En otros conjuntos, $ne puede incluir documentos sin el campo; aquí se fija el dataset para explicar el mecanismo.

La corrección se construye en cuatro decisiones

1. Declarar y aplicar el contrato

El campo debe ser una cadena de longitud acotada. Se rechazan objetos, listas y claves extra. En FastAPI, el parámetro de la ruta tiene que usar el modelo: declararlo sin conectarlo a la ruta no valida la petición.

2. Construir el filtro en el servidor

El cliente aporta un valor. El servidor conserva la estructura y utiliza igualdad. Una contraseña que contenga $ como carácter no se convierte por ello en una expresión.

3. Fijar el alcance del catálogo

La API selecciona únicamente fichas publicadas y devuelve los campos públicos necesarios. Una búsqueda de todos los productos públicos puede ser legítima; revelar borradores sería un fallo de autorización.

4. Limitar operación y respuesta

Acotar longitudes, campos y paginación reduce búsquedas imprevistas y consumo de recursos. El rol del motor sigue siendo necesario si alguien obtiene la credencial de la API.

# Esquema del filtro construido por el servidor
filtro = {"codigo": {"$eq": codigo_validado}, "publicado": True}
campos_publicos = {"_id": 0, "codigo": 1, "nombre": 1}
# La consulta limita también el número de resultados.
Con el objeto $ne, la defensa rechaza la estructura antes de consultar. Con P01, conserva el producto legítimo. Con P03, no devuelve el borrador. Cada resultado explica una decisión distinta.
El mismo principio en Elasticsearch

La aplicación recibe texto de búsqueda y construye un Query DSL con campos, índice y límite elegidos por el servidor. Una consulta match busca texto; no decide por sí sola si alguien puede ver un borrador.

{
  "size": 10,
  "_source": ["codigo", "nombre"],
  "query": {"bool": {
    "must": [{"match": {"nombre": "tomates"}}],
    "filter": [{"term": {"publicado": true}}]
  }}
}

El ejemplo presupone el mapping adecuado. El servidor fija esos nombres y recibe únicamente el texto autorizado. El rol debe limitar el índice accesible. La sintaxis mostrada no se envía a Elasticsearch desde esta página.

4.3 y 4.5 · Defensa por fronteras

Cada control responde a una pregunta diferente

Autenticar acredita una identidad. Autorizar decide qué puede hacer. La red determina desde dónde se alcanza el servicio. TLS protege el canal y permite validar al extremo. Una de estas capas no sustituye a las demás.

¿Quién se conecta?

La cuenta técnica se identifica ante MongoDB

La API presenta su credencial. El motor la verifica y asocia la conexión a lector_catalogo. Esto no identifica al visitante y todavía no decide qué colecciones puede leer esa cuenta.

APICredencial de servicio
→
MotorIdentidad lector_catalogo

Prueba positiva: la credencial válida permite conectar. Prueba negativa: la credencial incorrecta se rechaza. Luego habrá que probar los permisos de la conexión aceptada.

Ejemplo de configuración insegura: un laboratorio arranca MongoDB sin control de acceso y publica 27017:27017 en el host. El mapeo sin dirección escucha por defecto en las interfaces del host; no demuestra por sí solo acceso desde Internet. Usar 127.0.0.1:27017:27017 limita esa publicación a la interfaz local, mientras que retirar el puerto evita esa ruta desde el host. La red interna y los permisos siguen necesitando configuración.

La configuración efectiva depende del producto, la versión y el modo de despliegue. No todos los motores actuales arrancan abiertos. Verificar la interfaz, autenticación y reglas reales es más preciso que asumir un valor por defecto. Docker: publicación de puertos.

Añadir autenticación a MongoDB no arregla un filtro manipulable que la API ejecuta usando su propia cuenta válida.

El permiso mínimo protege también frente a una cuenta robada

Un filtro publicado=true protege la ruta que pasa por la API. Si la cuenta técnica puede leer toda la colección, alguien que robe esa cuenta puede saltarse el filtro. Para el diseño del caso, separamos los datos públicos de los borradores.

MongoDB concreta permisos sobre sus recursos; Redis puede restringir comandos y claves mediante ACL; Cassandra separa autenticación y autorización; Elasticsearch aplica privilegios sobre índices. Los nombres y la configuración efectiva dependen del motor.

Kubernetes aporta herramientas, pero hay que configurar la protección

Secret: distribuir un secreto con acceso limitado

El contenido de un Secret puede aparecer representado en Base64. Esa codificación se puede revertir sin una clave. La protección exige limitar quién lo lee, proteger su almacenamiento y restringir a qué contenedores se entrega.

c29sb19sYWJvcmF0b3Jpbw==

Ejemplo ficticio: cualquiera que vea esta representación puede decodificarla.

Si una credencial se publica en Git, borrar el archivo no invalida las copias que otros hayan obtenido. Hay que revocarla o rotarla y actualizar sus consumidores.

NetworkPolicy: limitar el tráfico que llega

Una política puede permitir la API del catálogo y negar pods ajenos. Para que tenga efecto, la red del clúster debe implementar NetworkPolicy. Crear un namespace por sí solo no aísla todas sus conexiones.

StatefulSet: identidad y almacenamiento estables

Ayuda a mantener identidad y volúmenes de los pods. La replicación, la pertenencia al clúster y la recuperación las configura el motor. Tres pods no se convierten automáticamente en tres réplicas correctas.

Además: proceso con permisos reducidos, imágenes mantenidas, límites de recursos, acceso al plano de control y copias de volúmenes con sus claves.

El despliegue se comprueba desde los orígenes reales: la API autorizada funciona, un origen ajeno no alcanza el motor y la credencial de lectura no administra ni borra.

4.4 · Disponibilidad y recuperación

Una réplica conserva los cambios, incluido un borrado

La replicación mantiene copias del estado para ayudar a continuar ante ciertos fallos. Una copia histórica conserva un estado al que podemos volver. Son dos objetivos diferentes.

En este ejemplo, una cuenta autorizada borra P01. El cambio se propaga a los miembros. Avanza para ver qué conserva cada copia y por qué hace falta una restauración histórica.

Estado inicial: los tres miembros contienen P01 y P02.

Secuencia explicativa, sin conexiones ni restauración de MongoDB. No representa una medición de RPO/RTO, una elección de primario ni garantiza ausencia de pérdida de datos.

Si el borrado ya está en todas las réplicas, cambiar a otra réplica no devuelve el producto. Se necesita un estado histórico válido y un procedimiento de recuperación probado.

Rotar una credencial es coordinar quién la acepta y quién la usa

Los miembros deben reconocerse entre sí. Si un nodo acepta únicamente una credencial nueva mientras los demás solo aceptan la antigua, pueden perder esa compatibilidad. El modelo permite ver el riesgo antes de pensar en un procedimiento concreto de producto.

La secuencia segura depende del mecanismo que admita el motor: preparar, distribuir, comprobar consumidores y miembros, y retirar la credencial antigua. El solapamiento K1/K2 es un modelo de compatibilidad, no una receta universal.

Si K1 está comprometida, mantenerla durante un solapamiento conserva temporalmente el riesgo. La contención, la urgencia de revocación y el procedimiento del producto determinan el orden real.

«Clave» puede referirse a tres cosas distintas

Clave de partición

Determina cómo se distribuyen o localizan datos. Ejemplo: dispositivo y fecha en la telemetría.

Credencial de acceso

Autentica a un cliente o miembro. Cambiarla exige actualizar a quienes la utilizan.

Clave de cifrado

Permite descifrar datos protegidos. Una copia antigua puede seguir necesitándola.

Rotar la contraseña de una aplicación no vuelve a cifrar sus copias. Eliminar una clave de cifrado antes de migrar y verificar esas copias puede impedir recuperarlas.

Resolución del problema

La API está corregida, pero una credencial administradora se ha filtrado

Ahora el motor tiene autenticación. El nuevo problema es que una cuenta de demasiado alcance apareció en Git y existe una ruta de red innecesaria hacia el motor. Activar otra vez la autenticación no resuelve esta exposición.

La solución debe retirar el acceso indebido y mantener el catálogo público. Este recorrido muestra una respuesta razonada y explica qué prueba confirma cada decisión.

  1. Delimitar
  2. Contener

1. Identificar la credencial y su alcance

Determinar qué cuenta se publicó, qué operaciones permite, qué servicios la usan y qué registros ayudan a reconstruir su uso. Preservar la evidencia sin volver a copiar el secreto.

Resultado: conocemos las superficies afectadas y quién puede ejecutar cada acción de respuesta.

Respuesta al problema inicial: la API valida su entrada; el motor limita identidades y recursos; la red reduce orígenes; los miembros y canales se protegen; la recuperación conserva una historia comprobable.

Una demostración completa conserva lo que debe funcionar

Ruta legítima

Visitante pide P01 → la API construye la consulta → su cuenta lectora accede al catálogo público → devuelve código y nombre.

Debe seguir funcionando. Confirma que la defensa no ha dejado inutilizado el servicio.

Ruta indebida

Objeto en lugar de código → rechazo de entrada. Credencial antigua → rechazo de autenticación. Lector que intenta borrar → denegación del permiso.

Cada rechazo pertenece a una capa. Un fallo de conexión no es un código HTTP.

Una API puede devolver 422 para el contrato inválido, 401 para una credencial no válida o 403 para una operación no autorizada según su diseño. El motor puede emitir un error nativo; una restricción de red puede impedir la conexión. La evidencia debe identificar qué control respondió.

Lo aprendido: para declarar segura una ruta necesitamos la petición, la identidad efectiva, el control que decide y el resultado. Bloquear un ataque sin comprobar la función legítima ofrece una conclusión incompleta.
